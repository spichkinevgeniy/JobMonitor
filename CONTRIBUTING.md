# Как помочь проекту

Можно исправить ошибку, предложить улучшение или добавить Telegram-канал с IT-вакансиями. Перед большой доработкой создайте issue и обсудите решение. Так меньше риск сделать ненужную работу.

Не добавляйте в репозиторий `.env`, сессии Telegram, токены, ключи API и данные продакшена.

## Ветки и pull request

Рабочий процесс:

1. Сделайте форк и создайте ветку от `main`.
2. Внесите небольшое законченное изменение.
3. Запустите проверки.
4. Отправьте ветку и откройте pull request в `main`.

Названия веток:

- `feature/<описание>` — новая возможность;
- `fix/<описание>` — исправление;
- `docs/<описание>` — документация.

В pull request напишите, что и зачем изменили, а также как проверили результат. Добавьте скриншоты для изменений интерфейса и предупредите о миграциях, новых переменных окружения или несовместимых изменениях.

## Как добавить Telegram-канал

Добавьте канал в `channels_map.json` и выберите ближайшую категорию. В pull request укажите, чем канал полезен, публичный ли он и на какой язык, регион или направление рассчитан.

Не добавляйте дубликаты и пустые значения. Полные правила описаны в [docs/CHANNELS.md](docs/CHANNELS.md).

## Локальная разработка

Понадобятся Python 3.12+, `uv` и PostgreSQL, если база работает не в Docker.

```bash
uv sync --dev
docker compose up -d db
uv run alembic upgrade head
uv run -m app.main
```

Полная настройка окружения и Telegram описана в [docs/INSTALL.md](docs/INSTALL.md).

## Стиль и проверки

Следуйте текущей структуре проекта. Не добавляйте параллельные абстракции без необходимости. Ruff использует длину строки 100 символов, MyPy работает в строгом режиме, целевая версия Python — 3.12.

Перед pull request запустите:

```bash
make quality
```

Команда проверяет Ruff, форматирование, MyPy и тесты. Для отдельных проверок доступны:

```bash
make lint
make test
make test-unit
make test-integration
```

Если изменение влияет на поведение, обновите тест. Если автоматическая проверка не подходит, объясните это в pull request.

## Релиз и выкладка

После слияния изменений в `main` создайте тег следующей версии:

```bash
git switch main
git pull --ff-only
make quality
git tag v0.1.2
git push origin v0.1.2
```

Тег `v*` запускает workflow `Релиз`: он проверяет проект и создаёт GitHub Release с автоматическими примечаниями.

Продакшен обновляется отдельно. В GitHub Actions запустите `Выкладка в продакшен`, укажите выпущенный тег в поле `ref`, например `v0.1.2`. Workflow проверит проект, подключится к серверу, пересоберёт контейнеры и применит миграции.

Для деплоя нужны секреты `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_PORT` и `VPS_APP_DIR`.

## Обращения

Перед созданием issue проверьте, что похожего обращения ещё нет. Для ошибки приложите шаги воспроизведения, ожидаемый и фактический результат, версию и полезные логи без секретов.

Об уязвимостях сообщайте по [правилам безопасности](SECURITY.md), а не через публичный issue.
